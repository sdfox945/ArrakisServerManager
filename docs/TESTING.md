# Test and acceptance checklist

Automated tests must never change the live VM, battlegroup, Kubernetes resources, configuration, credentials, networking, database or saves. Normal suite uses fixtures, local temporary directories and simulated infrastructure. The explicit read-only probe is separate. The UI smoke mode forcibly selects Demo even if `--demo` is omitted.

For v1.0.1, the complete suite also executes the real configuration script in a pinned BusyBox 1.37.0 Docker image. Development requires a running Linux Docker engine and the image pull documented in README; the application itself does not use Docker. Test containers use `--rm --network none --read-only` and a private `/work` tmpfs, with no host/production mounts. These cover the reported option rejection, real kernel-lock contention, write/rename/readback failures, atomic rollback, external-change refusal and state reconciliation. Native UI smoke also checks the save error/history detail views. See RELEASE-v1.0.1.md for the exact recovery and reversible live acceptance procedure.

## Recommended manual sequence

1. Start **Launch Demo.cmd**. Confirm the Demo label on every page, resize, use the keyboard, and try the Allocating, OOM, offline, SSH-failure and save-failure scenarios.
2. In Demo, test start/stop/restart, resource review/cancel/apply, raw/visual drafts, validation, undo, diff review, encrypted rollback/restore, simulated database backup/download and stopped-only restore. Confirm no browser/SSH process is used by Demo.
3. Launch Live. Confirm installation, VM address and existing key. Review a new fingerprint only after independent verification. Inspect actual host/guest RAM, swap, CPU, disk, maps and errors. Hyper-V may require account authorization or the read-only UAC snapshot.
4. Search `DLC_Story_LostHarvest_EcolabA`, inspect configured memory, usage, restarts, events and logs. Do not change allocation merely to test a button.
5. Load the three active INI files, inspect visual metadata and raw comments/custom keys. Make a draft and cancel the review. Verify server hashes remain unchanged. Try switching files/modes with a dirty draft and check the discard prompt.
6. Check running/downloaded revisions; open Director and File Browser after availability checks. Read/copy/filter bounded logs. Confirm directories and refresh thresholds persist on restart.
7. During a separately chosen maintenance window, with recovery access and independent backups, test official database backup first. Verify the completed remote artifact, download it, and compare size/hash. Keep a known good independent backup before testing any restore.
8. Only when ready for disruption, test stopped/started state transitions and graceful VM shutdown/start. Verify the state independently in Hyper-V/Director. Never test emergency power-off on a healthy world.
9. Exercise a small intentional configuration/resource change after reviewing values and backup paths. Confirm readback, reconciliation behavior and intended in-game effect; restore the reviewed previous configuration if appropriate. Client dependencies must be applied manually on the game client.
10. Test updates, database import, networking, passwords and experimental swap only when actually needed and with a recovery plan. These are implemented but are not established by development's read-only live checks. Supervise the official/native consoles. Never use production progress merely as a destructive test fixture.

Production-changing actions are **awaiting live acceptance**. Installer/signing, real multi-monitor DPI transitions, arbitrary local database-upload automation, SSH key rotation and unsupported Funcom layouts are outside validated claims. The native app advertises PerMonitorV2 scaling and uses WPF device-independent layout; manual monitor/DPI acceptance remains part of step 1/3.
